# Алгоритм ручной проверки функциональности и безопасности

Документ рассчитан на проверку после применения обеих миграций и создания трёх тестовых пользователей: одного `requester` и двух `executor`.

## 0. Подготовка тестовых данных

1. Создайте пользователя-постановщика `boss@example.com`.
2. Создайте исполнителей `worker1@example.com` и `worker2@example.com`.
3. Добавьте соответствующие строки в `public.profiles` с правильными UUID, email и ролями.
4. Войдите постановщиком и создайте два объекта.
5. Создайте минимум три задачи: две назначьте `worker1`, одну — `worker2`.
6. Сохраните UUID объектов и задач. Они понадобятся для прямых запросов к API.
7. Проверьте, что в Authentication отключена публичная регистрация.

Для чистой проверки используйте отдельные браузерные профили или выходите из системы перед входом под другой ролью.

## 1. Проверка авторизации

| Действие | Ожидаемый результат |
| --- | --- |
| Вход с правильным email и паролем | Пользователь входит в систему |
| Вход с неправильным паролем | Вход отклонён, данные CRM не показываются |
| Попытка публичной регистрации | Supabase отклоняет регистрацию |
| Вход пользователем без строки в `public.profiles` | Доступ к CRM не открывается, отображается сообщение о ненастроенном профиле |
| Выход | Сессия завершается, защищённые данные исчезают из интерфейса |

## 2. Проверка видимости данных по ролям

### Под постановщиком

- Видны все активные объекты.
- Видны все активные задачи.
- В форме задачи в списке исполнителей присутствуют пользователи с ролью `executor`, но не постановщики.
- Можно открыть карточку любой задачи и увидеть историю.

### Под исполнителем № 1

- Видны только назначенные ему активные задачи.
- Видны только активные объекты, к которым привязана хотя бы одна его задача.
- В «Мои задачи» нет задач исполнителя № 2.
- В карточке задачи отображается её автор и история, если они доступны по связанным с задачей профилям.

### Под исполнителем № 2

- Видны его назначенные задачи.
- Не видны задачи исполнителя № 1 и объекты, к которым у него нет назначенных активных задач.

Важно: проверьте данные не только визуально, но и через REST API (раздел 6). Скрытие элемента в React само по себе не является контролем доступа.

## 3. Проверка полного цикла статусов

Проверяйте на отдельной задаче и сверяйте статус после каждого действия.

| Шаг | Кто выполняет | Действие | Ожидаемый статус |
| --- | --- | --- | --- |
| 1 | Постановщик | Создаёт задачу | `Новая` |
| 2 | Назначенный исполнитель | Нажимает «Взять в работу» | `В работе` |
| 3 | Назначенный исполнитель | Нажимает «Отправить на проверку» | `На проверке` |
| 4а | Постановщик | Принимает задачу | `Принята` |
| 4б | Постановщик | Возвращает задачу с комментарием | `На доработке` |
| 5 | Назначенный исполнитель | Возвращает задачу в работу | `В работе` |

В ветке 4б проверьте, что пустой или состоящий из пробелов комментарий не позволяет отправить задачу на доработку. После возврата комментарий должен отображаться в истории.

## 4. Проверка запрещённых переходов

Проверяйте не только отсутствие кнопки в UI, но и серверный отказ. Для проверки прямого запроса используйте REST-примеры из следующего раздела.

- Исполнитель не может принять задачу (`review → accepted`).
- Исполнитель не может вернуть задачу на доработку (`review → rework`).
- Постановщик не может сам взять задачу в работу (`new → in_progress`).
- Постановщик не может отправить задачу на проверку (`in_progress → review`).
- Исполнитель не может перейти напрямую из `new` в `review`.
- Исполнитель не может перейти из `accepted` в другой статус.
- Исполнитель не может менять задачу, назначенную другому исполнителю.
- Исполнитель не может менять название, описание, объект, исполнителя и автора задачи.

Ожидаемый результат: запрос отклоняется PostgreSQL-триггером или RLS-политикой; данные в БД не изменяются.

## 5. Проверка CRUD и архивации

### Объекты

- Постановщик создаёт объект.
- Постановщик изменяет название и адрес.
- Исполнитель не может создать, изменить или архивировать объект.
- Архивирование объекта скрывает его из рабочих списков и архивирует связанные активные задачи.
- История задач остаётся в БД.

### Задачи

- Постановщик создаёт задачу с начальным статусом `new`.
- Постановщик изменяет название, описание, объект и исполнителя.
- Исполнитель не может изменить эти поля.
- Постановщик архивирует задачу; она исчезает из рабочих списков.
- Архивную задачу нельзя редактировать или восстановить через клиентский API.
- Физическое удаление задачи и истории через роль `authenticated` запрещено.

Архивация используется вместо физического удаления намеренно: иначе удаление задачи удалило бы или нарушило связь с её неизменяемой историей.

## 6. Проверка RLS прямыми REST-запросами

### Получение пользовательского access token

Выполните запрос для каждого тестового пользователя. URL проекта и publishable/anon key возьмите из настроек Supabase. Пароль и access token не сохраняйте в Git и не отправляйте третьим лицам.

```bash
curl -X POST "$SUPABASE_URL/auth/v1/token?grant_type=password" \
  -H "apikey: $SUPABASE_PUBLISHABLE_KEY" \
  -H "Content-Type: application/json" \
  -d '{"email":"worker1@example.com","password":"TEST_PASSWORD"}'
```

Из ответа возьмите `access_token`. Для остальных запросов используйте токен именно проверяемого пользователя:

```bash
curl "$SUPABASE_URL/rest/v1/tasks?select=id,title,assignee_id" \
  -H "apikey: $SUPABASE_PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $ACCESS_TOKEN"
```

### Исполнитель не читает чужие задачи

Запросите конкретную задачу, назначенную исполнителю № 2, используя токен исполнителя № 1:

```bash
curl "$SUPABASE_URL/rest/v1/tasks?id=eq.TASK_ID_WORKER_2&select=id,title,assignee_id" \
  -H "apikey: $SUPABASE_PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $WORKER_1_ACCESS_TOKEN"
```

Ожидаемый результат — пустой массив. Повторите с токеном исполнителя № 2: его задача должна быть доступна.

### Исполнитель не читает чужой объект

Запросите объект, на котором у исполнителя № 1 нет активных задач:

```bash
curl "$SUPABASE_URL/rest/v1/projects?id=eq.PROJECT_ID_WITHOUT_WORKER_1_TASK&select=id,name,address" \
  -H "apikey: $SUPABASE_PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $WORKER_1_ACCESS_TOKEN"
```

Ожидаемый результат — пустой массив. Если назначить этому исполнителю активную задачу на объекте, объект должен стать доступен.

### Email профилей недоступен клиенту

Выполните запрос `profiles?select=id,email` с любым пользовательским токеном. Запрос должен завершиться ошибкой прав на колонку `email`. При этом `profiles?select=id,full_name,role` должен возвращать только строки, разрешённые RLS.

### Исполнитель не меняет чужую задачу

```bash
curl -i -X PATCH "$SUPABASE_URL/rest/v1/tasks?id=eq.TASK_ID_WORKER_2" \
  -H "apikey: $SUPABASE_PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $WORKER_1_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Prefer: return=representation" \
  -d '{"title":"Несанкционированное изменение"}'
```

Ожидаемый результат — ни одна строка не изменена и не возвращена. RLS может представить недоступную строку как пустой результат, а не как явную ошибку; обязательно повторно прочитайте задачу токеном её владельца и убедитесь, что название не изменилось.

### Запрещённый переход не проходит напрямую через API

Например, токен исполнителя не должен позволить принять задачу:

```bash
curl -i -X PATCH "$SUPABASE_URL/rest/v1/tasks?id=eq.TASK_ID_WORKER_1" \
  -H "apikey: $SUPABASE_PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $WORKER_1_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Prefer: return=representation" \
  -d '{"status":"accepted"}'
```

Для этого теста задача должна принадлежать исполнителю и находиться в статусе, отличном от `accepted`. Ожидаемый результат — отказ PostgreSQL-триггера и отсутствие изменения статуса.

### Историю нельзя подделать или удалить

Попробуйте с пользовательским JWT выполнить INSERT, PATCH и DELETE для `task_status_history`. Все три действия должны завершиться отказом по привилегиям/политикам. Пример попытки вставки:

```bash
curl -i -X POST "$SUPABASE_URL/rest/v1/task_status_history" \
  -H "apikey: $SUPABASE_PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $WORKER_1_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"task_id":"TASK_ID_WORKER_1","actor_id":"WORKER_1_UUID","to_status":"accepted"}'
```

Ожидаемый результат — отказ в доступе. Затем выполните корректный переход из интерфейса: новая запись истории должна появиться автоматически, а поля `actor_id`, `from_status`, `to_status`, `created_at` должны соответствовать действию.

### Клиент не меняет профиль или роль

Попробуйте PATCH строки `profiles` с токеном исполнителя, изменив `role` на `requester`. Запрос должен быть отклонён. Дополнительно проверьте, что исполнитель не может создать профиль другого пользователя.

Попробуйте прочитать колонку `email` из `profiles` с пользовательским JWT. Запрос должен завершиться ошибкой прав доступа. Чтение `id`, `full_name` и `role` при этом разрешено в пределах RLS-политики.

### Важно о SQL Editor

SQL Editor выполняет запросы с административными правами и не доказывает корректность RLS для обычного пользователя. Для проверок доступа используйте пользовательский JWT через REST API или авторизованный клиент приложения. Не используйте `service_role` / secret key в этих тестах.

## 7. Проверка истории

Для задачи пройдите весь цикл и проверьте:

- при создании есть запись `— → Новая`;
- после каждого успешного перехода появляется ровно одна новая запись;
- в записи указан действовавший пользователь;
- время создания записи заполнено базой данных;
- комментарий есть у возврата на доработку;
- обе роли могут читать историю своей задачи;
- через пользовательский API нельзя вставить, обновить или удалить историю.

## 8. Финальный регрессионный проход

1. Перезагрузите страницу под постановщиком и исполнителем: сессия должна восстановиться.
2. Создайте объект и задачу, затем отредактируйте их.
3. Проведите одну задачу по ветке принятия, другую — по ветке доработки.
4. Убедитесь, что исполнитель № 1 не видит задачи исполнителя № 2.
5. Архивируйте одну задачу и один объект; проверьте исчезновение из рабочих списков.
6. Через административный SQL Editor убедитесь, что записи `task_status_history` архивированных задач не удалены.
7. Выйдите и убедитесь, что интерфейс возвращается к форме входа.
8. Запустите `pnpm typecheck` и `pnpm build`.

## Критерий успешной проверки

Функциональность считается проверенной, когда все разрешённые действия выполняются, запрещённые действия блокируются сервером даже при прямом REST-запросе, данные исполнителей изолированы, а история переходов сохраняется и не редактируется пользовательскими ролями.
