# СтройКонтроль — мини-CRM «Объекты и задачи»

Мини-CRM для строительной компании. Постановщики ведут объекты и задачи, исполнители работают только со своими задачами, суперадминистратор управляет учётными записями сотрудников.

## Стек технологий

- React 18
- TypeScript
- Vite
- Supabase Auth
- PostgreSQL
- Row Level Security (RLS)
- Supabase Edge Functions
- pnpm

## Возможности

### Суперадминистратор (`superadmin`)

- Создаёт учётные записи постановщиков и исполнителей.
- Просматривает список пользователей, email и роли.
- Назначает и меняет роли `requester` и `executor`.
- Не имеет доступа к объектам, задачам и истории задач.
- Не может изменить собственную роль или роль другого суперадминистратора.
- Не может создавать дополнительных суперадминистраторов через интерфейс CRM.

### Постановщик (`requester`)

- Видит все активные объекты и задачи.
- Создаёт, редактирует и архивирует объекты.
- Создаёт, редактирует и архивирует задачи.
- Назначает исполнителей.
- Принимает задачи или возвращает их на доработку с обязательным комментарием.
- Просматривает историю всех задач.

### Исполнитель (`executor`)

- Видит только назначенные ему активные задачи и связанные с ними объекты.
- Может взять задачу в работу.
- Может отправить задачу на проверку.
- Может повторно взять задачу в работу после возврата на доработку.
- Не может менять описание, объект, автора или исполнителя задачи.
- Видит историю только доступных ему задач.

## Локальный запуск

Клонируйте репозиторий:

```bash
git clone https://github.com/Symegu/mini-crm.git
cd mini-crm
```

Установите зависимости:

```bash
pnpm install
```

Создайте локальный файл окружения.

Windows PowerShell:

```powershell
Copy-Item .env.example .env.local
```

Linux / macOS:

```bash
cp .env.example .env.local
```

Заполните `.env.local`:

```env
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_SUPABASE_PUBLISHABLE_OR_ANON_KEY
```

`VITE_SUPABASE_ANON_KEY` принимает современный Publishable key или legacy anon key.

**Важно:** все переменные с префиксом `VITE_` доступны в браузере. Запрещено помещать в них `service_role`, Secret key и другие серверные секреты.

Запуск приложения:

```bash
pnpm dev
```

Проверка проекта:

```bash
pnpm typecheck
pnpm build
pnpm preview
```

## Настройка Supabase

### 1. Подключение проекта

Выполните команды из корня проекта:

```bash
npx supabase login
npx supabase link --project-ref YOUR_PROJECT_REF
```

`YOUR_PROJECT_REF` — Reference ID проекта из Supabase Dashboard → Project Settings → General.

### 2. Применение миграций

Миграции находятся в `supabase/migrations/`.

Для нового проекта выполните:

```bash
npx supabase migration list --linked
npx supabase db push
```

Миграции применяются последовательно:

| Файл | Назначение |
|---|---|
| `202611050001_initial_schema.sql` | Основные таблицы, роли, статусы, функции, триггеры и RLS |
| `202611050002_archive_records_and_lock_audit.sql` | Архивирование, защита истории и переходы статусов |
| `202611050003_add_superadmin_role.sql` | Добавление роли `superadmin` |
| `202611050004_secure_profiles_for_admin.sql` | Ограничение доступа к профилям и защита изменения ролей |

`npx supabase db push` применяет миграции, отсутствующие в истории удалённой базы.

**Важно:**
- Не запускайте `npx supabase db reset` на рабочей базе.
- Не запускайте старый `supabase/setup.sql` повторно на базе с данными: он предназначен для полной переустановки.
- Если схема создавалась вручную через SQL Editor, сначала проверьте историю миграций и соответствие фактической схемы файлам миграций.
- `migration repair` изменяет историю миграций, но не выполняет SQL. Нельзя отмечать миграцию применённой, пока её SQL действительно не выполнен.

Если миграции уже выполнялись вручную, проверьте их состояние:

```bash
npx supabase migration list --linked
```

Не применяйте повторно уже существующие объекты без предварительной проверки.

### 3. Отключение публичной регистрации

В Supabase Dashboard откройте настройки Authentication → Providers → Email.

Отключите параметр **Allow new users to sign up**.

Самостоятельная регистрация в CRM не предусмотрена. Учётные записи создаются владельцем проекта или суперадминистратором.

### 4. Публикация Edge Function

Административные операции выполняются через серверную функцию:

```bash
npx supabase functions deploy admin-users
```

Функция находится в:

```text
supabase/functions/admin-users/index.ts
```

Поддерживаемые операции:

- `list` — получение списка пользователей;
- `create` — создание пользователя;
- `update_role` — изменение роли пользователя.

Перед выполнением административной операции функция проверяет JWT и роль вызывающего пользователя.

В `supabase/config.toml` включена проверка JWT:

```toml
[functions.admin-users]
verify_jwt = true
```

Административный клиент Supabase используется только на серверной стороне Edge Function. Секретные ключи не должны попадать во frontend-код.

### 5. Создание первого суперадминистратора

Первый суперадминистратор создаётся вручную владельцем Supabase.

**Шаг 1. Создайте Auth-пользователя.**

1. Откройте Supabase Dashboard.
2. Перейдите в Authentication → Users.
3. Нажмите Add user.
4. Укажите email и пароль.
5. Создайте пользователя.

**Шаг 2. Создайте профиль.**

Откройте SQL Editor → New query.

Замените email и имя на данные созданного пользователя:

```sql
DO $$
DECLARE
    v_user_id UUID;
    v_email TEXT := 'admin@company.ru';
    v_full_name TEXT := 'Главный администратор';
BEGIN
    SELECT id
    INTO v_user_id
    FROM auth.users
    WHERE lower(email) = lower(v_email)
    LIMIT 1;

    IF v_user_id IS NULL THEN
        RAISE EXCEPTION 'Сначала создайте пользователя % в Supabase Auth', v_email;
    END IF;

    INSERT INTO public.profiles (id, full_name, email, role)
    VALUES (v_user_id, v_full_name, lower(v_email), 'superadmin')
    ON CONFLICT (id) DO UPDATE
    SET
        full_name = EXCLUDED.full_name,
        email = EXCLUDED.email,
        role = 'superadmin';
END;
$$;
```

Если база ещё не содержит роль `superadmin`, сначала примените миграцию `202611050003_add_superadmin_role.sql` и убедитесь, что она завершилась успешно.

**Шаг 3. Войдите в приложение.**

Используйте email и пароль созданного Auth-пользователя.

После успешной загрузки профиля станет доступен раздел «Пользователи».

### 6. Управление пользователями

В разделе «Пользователи» суперадминистратор может:

- создавать учётные записи;
- задавать ФИО, email и временный пароль;
- выбирать роль постановщика или исполнителя;
- менять роли существующих пользователей.

Ограничения:

- разрешены только роли `requester` и `executor`;
- нельзя изменить собственную роль;
- нельзя изменить роль существующего суперадминистратора;
- нельзя перевести исполнителя в постановщики, пока за ним числятся активные задачи;
- удаление пользователей и сброс пароля через интерфейс CRM не реализованы.

Роли фиксированные, динамическое создание ролей не предусмотрено.

## Публикация проекта в Vercel

Vercel используется для сборки и публикации frontend-приложения.

### 1. Подключение GitHub

1. Откройте Vercel.
2. Нажмите Add New → Project.
3. Подключите GitHub, если он ещё не подключён.
4. Выберите репозиторий `Symegu/mini-crm`.
5. Укажите ветку `main`.

Настройки сборки:

| Параметр | Значение |
|---|---|
| Framework Preset | Vite |
| Build Command | `pnpm build` |
| Install Command | `pnpm install` |
| Output Directory | `dist` |
| Root Directory | `./` |

Если Vercel определил настройки автоматически и они соответствуют проекту, менять их не требуется.

### 2. Настройка Environment Variables

Откройте:

**Vercel → Project → Settings → Environment Variables**

Добавьте две переменные:

| Name | Value |
|---|---|
| `VITE_SUPABASE_URL` | URL проекта Supabase |
| `VITE_SUPABASE_ANON_KEY` | Publishable key или legacy anon key |

Выберите необходимые окружения:

- Production
- Preview
- Development

Сохраните переменные.

После изменения ENV выполните новый Deployment, чтобы значения попали в сборку.

**Безопасность:**

Публичные параметры Supabase предназначены для использования во frontend-приложении. Они не заменяют RLS и не предоставляют автоматически полный доступ к базе.

Никогда не добавляйте следующие секреты во frontend-переменные:

- `SUPABASE_SERVICE_ROLE_KEY`
- `SUPABASE_SECRET_KEY`
- другие административные ключи Supabase.

Не создавайте переменные `VITE_SERVICE_ROLE_KEY` или `VITE_SUPABASE_SECRET_KEY`.

### 3. Как обновлять опубликованное приложение

При подключённом GitHub каждый push в `main` запускает новый Production Deployment.

Изменения README, SQL-миграций и Edge Function сами по себе не выполняются через Vercel.

Необходимо отдельно:

- отправлять код в GitHub;
- применять SQL-миграции через Supabase CLI;
- публиковать Edge Function через Supabase CLI.

Vercel отвечает только за сборку и публикацию frontend-приложения.

## Модель ролей и прав

| Возможность | Суперадмин | Постановщик | Исполнитель |
|---|:---:|:---:|:---:|
| Создавать пользователей | Да | Нет | Нет |
| Просматривать список пользователей | Да | Нет | Нет |
| Назначать рабочие роли | Да | Нет | Нет |
| Просматривать все объекты | Нет | Да | Нет |
| Просматривать все задачи | Нет | Да | Нет |
| Просматривать назначенные задачи | Нет | Да | Да |
| Создавать и редактировать объекты | Нет | Да | Нет |
| Создавать и редактировать задачи | Нет | Да | Нет |
| Менять статус задачи | Нет | Да | Да |
| Читать историю задач | Нет | Да | Только своих задач |

Фактические права обеспечиваются на стороне Supabase:

- RLS ограничивает чтение и изменение строк;
- триггеры и RPC контролируют допустимые переходы статусов;
- Edge Function проверяет JWT и роль суперадминистратора;
- обычный клиентский API не может напрямую менять роли и историю статусов.

## Статусы задач

| Из | В | Кто |
|---|---|---|
| — | `new` | Постановщик |
| `new` | `in_progress` | Исполнитель |
| `in_progress` | `review` | Исполнитель |
| `review` | `accepted` | Постановщик |
| `review` | `rework` | Постановщик, комментарий обязателен |
| `rework` | `in_progress` | Исполнитель |

Все остальные переходы запрещены на стороне PostgreSQL.

Каждое изменение статуса записывается в `task_status_history`.

## Безопасность учётных записей

- Пароли хранятся и обрабатываются средствами Supabase Auth.
- CRM не хранит пароли в таблице `profiles`.
- Административные операции выполняются через Edge Function.
- Публичная регистрация отключена.
- Секретные ключи не используются в frontend-коде.
- Временные пароли передаются сотрудникам по защищённому каналу.
- Смена пароля и восстановление доступа через интерфейс CRM пока не реализованы.

## Архивирование

Удаление объектов и задач реализовано через архивирование с использованием `archived_at`.

Архивные записи скрываются из рабочих списков, но остаются в базе.

При архивировании объекта связанные активные задачи также архивируются. История задач сохраняется.

## Ограничения тестовой версии

- Публичная регистрация отсутствует.
- Создание дополнительных суперадминистраторов через UI запрещено.
- Смена и сброс пароля через CRM не реализованы.
- Удаление учётных записей через CRM не реализовано.
- Уведомления, вложения, realtime и автоматизированные e2e-тесты не входят в текущую версию.
