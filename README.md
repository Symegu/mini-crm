# СтройКонтроль — мини-CRM «Объекты и задачи»

Мини-CRM для строительной компании. Постановщики ведут объекты и задачи, исполнители работают только со своими задачами, суперадминистратор создаёт учётные записи и назначает роли.

## Стек

- React 18 + TypeScript
- Vite
- Supabase Auth + PostgreSQL + Row Level Security (RLS)
- Supabase Edge Functions для административных операций
- pnpm

## Возможности

### Суперадминистратор (`superadmin`)

- Создаёт учётные записи постановщиков и исполнителей.
- Назначает и меняет роли `requester` и `executor`.
- Просматривает список пользователей, email и роли.
- Не получает доступ к объектам, задачам и истории задач.
- Не может через интерфейс создать второго суперадминистратора, изменить роль существующего суперадминистратора или изменить собственную роль.

### Постановщик (`requester`)

- Видит все активные объекты и задачи.
- Создаёт, редактирует и архивирует объекты.
- Создаёт, редактирует и архивирует задачи.
- Назначает исполнителей.
- Принимает задачи или возвращает на доработку с обязательным комментарием.
- Видит историю всех задач.

### Исполнитель (`executor`)

- Видит только назначенные ему активные задачи и объекты, к которым относятся эти задачи.
- Может переводить задачи `new → in_progress`, `in_progress → review` и `rework → in_progress`.
- Не может менять описание, объект, автора или исполнителя задачи.
- Видит историю только доступных ему задач.

## Требования

- Node.js `>=22.12.0`
- pnpm `12.16.1`
- Проект Supabase
- Supabase CLI для применения миграций и публикации Edge Function

Установка pnpm без Corepack:

```bash
npm install --global pnpm@12.16.1
```

## Локальный запуск

```bash
pnpm install
```

Создайте `.env.local` на основе `.env.example`.

PowerShell:

```powershell
Copy-Item .env.example .env.local
```

Заполните публичные параметры проекта:

```env
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_SUPABASE_PUBLISHABLE_OR_ANON_KEY
```

`VITE_SUPABASE_ANON_KEY` принимает legacy anon key или современный publishable key. В переменные Vite нельзя добавлять `service_role`, `secret` key или другие серверные секреты: все переменные `VITE_*` доступны в браузере.

Запуск и проверка:

```bash
pnpm dev
pnpm typecheck
pnpm build
pnpm preview
```

## Настройка Supabase: первый запуск

В этом разделе приведён полный порядок настройки нового проекта Supabase: от применения миграций до входа под первым суперадминистратором.

### 1. Применить миграции базы данных

Миграции находятся в `supabase/migrations/` и применяются по порядку. Для нового проекта выполните из корня репозитория:

```bash
npx supabase login
npx supabase link --project-ref YOUR_PROJECT_REF
npx supabase migration list --linked
npx supabase db push
```

Замените `YOUR_PROJECT_REF` на Reference ID проекта из Supabase Dashboard → Project Settings → General. Команда `db push` применит миграции, которых ещё нет в истории удалённой базы.

Миграции проекта:

1. `202611050001_initial_schema.sql` — таблицы профилей, объектов, задач и истории; роли и статусы; базовые функции, триггеры и RLS.
2. `202611050002_archive_records_and_lock_audit.sql` — архивирование объектов и задач, защита аудита и серверные переходы статусов.
3. `202611050003_add_superadmin_role.sql` — добавление роли `superadmin` в enum `app_role`.
4. `202611050004_secure_profiles_for_admin.sql` — ограничение чтения профилей и запрет изменения ролей через обычный клиентский API.

**Не запускайте `npx supabase db reset` на рабочей или содержащей нужные данные базе.** Эта команда предназначена для сброса локальной базы разработки.

#### Если схема уже была создана вручную

Если миграции `001` и `002` уже выполнялись в SQL Editor и соответствующая схема действительно присутствует в базе, не запускайте их повторно вручную. Проверьте историю:

```bash
npx supabase migration list --linked
```

Если `001` и `002` были выполнены вручную, но отсутствуют в таблице истории миграций, сначала убедитесь, что все объекты этих миграций уже существуют и соответствуют текущим файлам. Только после такой проверки можно отметить их как применённые:

```bash
npx supabase migration repair --status applied 202611050001 --linked
npx supabase migration repair --status applied 202611050002 --linked
```

Затем примените новые миграции `003` и `004` через `npx supabase db push` либо выполните их по отдельности в SQL Editor в указанном порядке и отметьте как применённые:

```bash
npx supabase migration repair --status applied 202611050003 --linked
npx supabase migration repair --status applied 202611050004 --linked
```

`migration repair` меняет только историю миграций — она **не выполняет SQL**. Не отмечайте миграцию как применённую, если её SQL на самом деле не был выполнен. Если база была создана старым `setup.sql` или отличается от файлов `001`/`002`, сначала сравните схему и сделайте резервную копию; не выполняйте команды `repair` вслепую.

### 2. Отключить публичную регистрацию

В Supabase Dashboard откройте настройки Auth и Email provider. Выключите параметр **Allow new users to sign up**. После этого пользователи смогут входить только после того, как их учётную запись создаст владелец проекта или суперадминистратор.

Отключение публичной регистрации не мешает владельцу Supabase вручную добавить первого пользователя через Dashboard. Также оно не мешает Edge Function создавать пользователей через Auth Admin API.

### 3. Опубликовать Edge Function для управления пользователями

Из корня репозитория выполните:

```bash
npx supabase functions deploy admin-users
```

Функция находится в `supabase/functions/admin-users/index.ts`. Она поддерживает три действия:

- `list` — получить список пользователей;
- `create` — создать пользователя и его профиль;
- `update_role` — изменить роль существующего пользователя.

Каждый запрос функции проходит две проверки:

1. `withSupabase({ auth: 'user' })` проверяет JWT вошедшего пользователя.
2. Функция читает профиль вызывающего пользователя и продолжает работу, только если его роль — `superadmin`.

Только внутри Edge Function используется административный клиент Supabase, который может обходить RLS для операций с Auth и таблицей `profiles`. Секреты Supabase предоставляются серверной средой Supabase; вручную копировать секретный ключ в React-приложение не нужно. В `supabase/config.toml` для этой функции включён `verify_jwt = true` — не отключайте эту проверку для пользовательского административного интерфейса.

### 4. Создать первого суперадминистратора

Первый `superadmin` создаётся вручную владельцем Supabase один раз. Это bootstrap-процедура: пока в базе нет суперадминистратора, назначить эту роль через интерфейс CRM некому.

**Шаг 1. Создайте Auth-пользователя в Dashboard.**

1. Откройте Supabase Dashboard → **Authentication → Users**.
2. Нажмите **Add user** и выберите создание нового пользователя (не публичную регистрацию).
3. Укажите email и пароль первого администратора.
4. Создайте пользователя и убедитесь, что он подтверждён. В CRM используется вход по email и паролю.

**Шаг 2. Создайте ему профиль с ролью `superadmin`.**

Откройте **SQL Editor → New query**, замените email и имя в начале запроса на данные только что созданного Auth-пользователя и выполните запрос:

```sql
DO $$
DECLARE
    v_user_id UUID;
    v_email TEXT := 'admin@company.ru'; -- замените на email Auth-пользователя
    v_full_name TEXT := 'Главный администратор'; -- замените на имя
BEGIN
    SELECT id
    INTO v_user_id
    FROM auth.users
    WHERE lower(email) = lower(v_email)
    LIMIT 1;

    IF v_user_id IS NULL THEN
        RAISE EXCEPTION 'Сначала создайте пользователя % в Supabase Auth', v_email;
    END IF;

    INSERT INTO public.profiles (id, full_name, email, role)
    VALUES (v_user_id, v_full_name, lower(v_email), 'superadmin')
    ON CONFLICT (id) DO UPDATE
    SET full_name = EXCLUDED.full_name,
        email = EXCLUDED.email,
        role = 'superadmin';
END;
$$;
```

Запрос связывает Auth-пользователя с профилем CRM по одному UUID. Пароль в таблицу `profiles` не записывается.

**Шаг 3. Войдите в приложение.**

Убедитесь, что в `.env.local` указаны URL и публичный ключ именно этого Supabase-проекта, запустите `pnpm dev` или откройте опубликованное приложение и войдите с email и паролем первого администратора. После загрузки профиля CRM откроет раздел **«Пользователи»**.

Если после входа открывается экран «Профиль не найден», проверьте, что SQL-запрос выполнился без ошибки, email совпадает с Auth-пользователем, а запись существует в `public.profiles`.

**Важно:** не выдавайте `superadmin` обычным пользователям. Создание дополнительных суперадминистраторов через интерфейс намеренно запрещено. Это можно сделать только вручную владельцем базы через доверенный SQL Editor после проверки личности пользователя.

### 5. Создавать пользователей и назначать им роли через CRM

После входа под `superadmin` откройте раздел **«Пользователи»**.

#### Создание пользователя

В блоке **«Создать пользователя»** заполните:

1. **ФИО** — отображаемое имя сотрудника.
2. **Email** — адрес, с которым сотрудник будет входить.
3. **Временный пароль** — от 12 до 128 символов.
4. **Роль** — `Постановщик` или `Исполнитель`.

Нажмите **«Создать пользователя»**. Edge Function создаст запись в Supabase Auth, подтвердит email и добавит связанный профиль в `public.profiles`. После успешного создания передайте сотруднику email и временный пароль по защищённому каналу. Поскольку email подтверждается при создании, дополнительное подтверждение для первого входа не требуется.

#### Изменение роли

В таблице пользователей найдите нужную учётную запись, выберите новую роль в выпадающем списке и нажмите **«Сохранить»**. Изменение применится на сервере после повторной проверки роли суперадминистратора.

Ограничения интерфейса и серверной функции:

- назначить можно только `requester` или `executor`;
- нельзя изменить собственную роль;
- нельзя изменить роль существующего `superadmin`;
- нельзя перевести исполнителя в постановщики, пока за ним числятся активные задачи — сначала переназначьте или архивируйте эти задачи;
- удаление пользователей и смена/сброс пароля из интерфейса CRM пока не реализованы.

**В текущей версии роли не создаются динамически.** В системе заранее определены три роли (`superadmin`, `requester`, `executor`), а интерфейс суперадминистратора создаёт пользователей и назначает им одну из двух рабочих ролей. Права каждой роли заранее реализованы в PostgreSQL RLS, серверных функциях и интерфейсе приложения.

## Модель ролей и прав

| Возможность | Суперадмин | Постановщик | Исполнитель |
| --- |:---:|:---:|:---:|
| Создавать пользователей | Да | Нет | Нет |
| Просматривать email и список пользователей | Да, через Edge Function | Нет | Нет |
| Назначать роли `requester` / `executor` | Да | Нет | Нет |
| Создавать других суперадминистраторов через CRM | Нет | Нет | Нет |
| Просматривать все объекты и задачи | Нет | Да | Нет |
| Просматривать назначенные задачи | Нет | Да | Да |
| Создавать и редактировать объекты | Нет | Да | Нет |
| Создавать и редактировать задачи | Нет | Да | Нет |
| Менять статус задачи | Нет | Принять / вернуть на доработку | Взять в работу / отправить на проверку |
| Читать историю задачи | Нет | Да | Для своих задач |

Роль хранится в `public.profiles.role`. Интерфейс лишь показывает доступные действия, а фактический доступ проверяется на стороне Supabase:

- PostgreSQL RLS ограничивает чтение и изменение строк;
- триггеры и RPC проверяют допустимые переходы статусов;
- Edge Function проверяет JWT и роль `superadmin` перед административными действиями;
- клиентский API не может напрямую менять роли и изменять историю статусов.

Суперадминистратор предназначен для управления учётными записями и не получает права постановщика автоматически.

## Статусы задач

| Из | В | Кто |
| --- | --- | --- |
| — | `new` | Постановщик при создании |
| `new` | `in_progress` | Назначенный исполнитель |
| `in_progress` | `review` | Назначенный исполнитель |
| `review` | `accepted` | Постановщик |
| `review` | `rework` | Постановщик, комментарий обязателен |
| `rework` | `in_progress` | Назначенный исполнитель |

Все остальные переходы запрещены на стороне PostgreSQL. Каждое изменение статуса записывается в `task_status_history` триггером. Клиентским ролям запрещены INSERT, UPDATE и DELETE этой таблицы.

## Пароли и безопасность учётных записей

- CRM не хранит пароли в `profiles` или собственных таблицах.
- Пароли передаются в Supabase Auth через серверный Auth Admin API и обрабатываются механизмом хранения паролей Supabase.
- `service_role` / secret key доступен только серверной Edge Function и никогда не включается в Vite-переменные, frontend-код или Git.
- Публичная регистрация отключена; в интерфейсе CRM нет страницы самостоятельной регистрации.
- Временный пароль передавайте пользователю отдельно от email или по другому защищённому каналу.
- Смена пароля и восстановление доступа из интерфейса CRM пока не реализованы. Для этого используйте штатные инструменты Supabase Auth.

## Архивирование

Удаление объектов и задач реализовано как архивирование через `archived_at`. Архивные записи скрываются из рабочих списков, а история остаётся в базе. Архивирование объекта архивирует связанные активные задачи.

## Что не входит в тестовую версию

- Публичная регистрация.
- Создание дополнительных суперадминистраторов через UI.
- Смена/сброс пароля из интерфейса CRM.
- Удаление учётных записей из CRM.
- Уведомления, вложения, realtime и автоматизированные e2e-тесты.
- Развёртывание фронтенда и создание реальных тестовых пользователей в чужом Supabase-проекте.

Краткое объяснение системы для руководителя находится в `docs/EXPLANATION-FOR-MANAGER.md`. Принятые решения и ограничения описаны в `PROJECT_NOTES.md`. Подробный чек-лист ручной проверки находится в `docs/SECURITY-AND-FUNCTIONAL-TEST-PLAN.md`.
