# mini-crm

Мини-CRM для строительной компании. Постановщик управляет объектами и назначает задачи, исполнители выполняют назначенную работу и передают её на проверку.

## Технологии

- React 18 + TypeScript
- Vite 8
- Supabase Auth
- PostgreSQL + Row Level Security (RLS)
- pnpm 12

## Требования

- Node.js 22.12 или новее
- Corepack или установленный pnpm
- Аккаунт Supabase

## Локальный запуск

Перейдите в корень проекта — папку, в которой находится `package.json`.

Установка зависимостей:

```bash
corepack pnpm --version
corepack pnpm install
```

В проекте указана версия пакетного менеджера `pnpm@12.16.1`. Corepack использует её из `package.json`.

Если pnpm уже установлен отдельно, можно использовать команды `pnpm install`, `pnpm dev` и другие без Corepack.

После установки проверьте, что создан файл `pnpm-lock.yaml`, и добавьте его в Git. Он фиксирует версии зависимостей и обеспечивает повторяемую установку проекта.

Создайте локальный файл окружения:

```bash
cp .env.example .env.local
```

На Windows PowerShell:

```powershell
Copy-Item .env.example .env.local
```

Заполните `.env.local` параметрами своего Supabase-проекта:

```env
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_SUPABASE_PUBLISHABLE_KEY
```

Переменная `VITE_SUPABASE_ANON_KEY` исторически названа `ANON_KEY`, но принимает современный Supabase publishable key (`sb_publishable_...`) или legacy anon key.

**Не добавляйте в `.env.local` и код клиентского приложения секретный `service_role` / `sb_secret` key.**

Запуск dev-сервера:

```bash
corepack pnpm dev
```

Production-сборка и локальный просмотр:

```bash
corepack pnpm typecheck
corepack pnpm build
corepack pnpm preview
```

## Настройка Supabase

### 1. Создание проекта и настройка базы

Создайте проект в Supabase и откройте **SQL Editor**.

Выполните файл `supabase/setup.sql` целиком от имени `postgres`.

> **ВНИМАНИЕ: ПОЛНЫЙ СБРОС.** Перед созданием схемы `setup.sql` удаляет таблицы и данные CRM (`profiles`, `projects`, `tasks`, `task_status_history`), функции, триггеры, политики и типы, а также записи двух старых миграций проекта из `supabase_migrations.schema_migrations`. Повторный запуск снова удалит все данные CRM. Запускайте файл только в тестовом Supabase-проекте.

Скрипт не удаляет пользователей из **Authentication → Users**, не меняет системные схемы Supabase и не удаляет расширения. Если старые тестовые Auth-пользователи остались, можно использовать их UUID повторно либо удалить их вручную в **Authentication → Users**.

В этой версии проекта миграционная история заменена единым SQL-файлом установки схемы. Для настройки используются два файла:

- `supabase/setup.sql` — сброс старой CRM-схемы и создание актуальной БД.
- `supabase/seed.sql` — заполнение демонстрационными объектами и задачами.

Не запускайте `supabase db push` для этой версии проекта: папки `supabase/migrations` нет.

### 2. Отключение открытой регистрации

В настройках Supabase Auth отключите параметр **Allow new users to sign up**.

Это соответствует требованиям задания: пользователи создаются администратором вручную, публичная регистрация в приложении отсутствует.

### 3. Создание тестовых пользователей

В разделе **Authentication → Users** создайте три пользователя через **Add user → Create new user**.

| Email | Роль в CRM |
| --- | --- |
| `boss@test.local` | Постановщик (`requester`) |
| `worker1@test.local` | Исполнитель (`executor`) |
| `worker2@test.local` | Исполнитель (`executor`) |

Для каждого пользователя задайте пароль и включите **Auto Confirm User**, чтобы тестовые аккаунты могли входить без подтверждения письма.

Сохраните UUID каждого пользователя из Authentication → Users.

### 4. Создание профилей CRM и назначение ролей

После создания Auth-пользователей выполните в SQL Editor запрос ниже, заменив UUID на фактические значения из Authentication → Users:

```sql
INSERT INTO public.profiles
  (id, full_name, email, role)
VALUES
  ('UUID_ПОСТАНОВЩИКА',
   'Иван Петров',
   'boss@test.local',
   'requester'),

  ('UUID_ИСПОЛНИТЕЛЯ_1',
   'Алексей Смирнов',
   'worker1@test.local',
   'executor'),

  ('UUID_ИСПОЛНИТЕЛЯ_2',
   'Дмитрий Волков',
   'worker2@test.local',
   'executor');
```

Каждый `id` должен совпадать с UUID соответствующего пользователя в `auth.users`, а email — с его Auth email.

Значение `role` назначает роль именно внутри CRM:

- `requester` — постановщик;
- `executor` — исполнитель.

Это не создание пользователей и не изменение системной роли Supabase Auth.

Выполняйте запрос от имени `postgres` после создания всех трёх пользователей в **Authentication → Users**.

Профили и роли назначаются администратором через SQL Editor. Клиентскому приложению запись и изменение ролей запрещены.

Запрос рассчитан на первое заполнение после `setup.sql`. При повторном выполнении для тех же пользователей возникнет конфликт уникальности.

### 5. Загрузка тестовых объектов и задач

Выполните `supabase/seed.sql` целиком в SQL Editor от имени `postgres`.

Скрипт добавит:

- 3 строительных объекта;
- 6 задач;
- задачи во всех пяти статусах: `new`, `in_progress`, `review`, `accepted`, `rework`;
- историю переходов статусов для каждой задачи.

Скрипт не создаёт временные таблицы, не выключает защитные триггеры и не обходит бизнес-правила: сначала создаёт задачи в `new`, затем проводит их по разрешённым переходам с тестовым JWT-контекстом пользователей.

Seed можно запускать повторно: существующие активные демо-объекты и задачи не дублируются и не перезаписываются. Если не хватает профиля постановщика или двух исполнителей, скрипт завершится с ошибкой.

> `seed.sql` предназначен только для тестовой базы. Не запускайте его в production-проекте с реальными данными.

## Файлы Supabase

```text
supabase/
├── setup.sql   # Полный сброс CRM-схемы и создание актуальной БД
└── seed.sql    # Три демо-объекта, шесть задач и история переходов
```

## Роли и функциональность

### Постановщик

- Видит все активные объекты и задачи.
- Создаёт, редактирует и архивирует объекты.
- Создаёт, редактирует и архивирует задачи.
- Назначает исполнителя из пользователей с ролью `executor`.
- Принимает задачу со статусом `review` или возвращает её на доработку с обязательным комментарием.

### Исполнитель

- Видит только задачи, назначенные ему, и активные объекты, в которых есть его задачи.
- Может перевести задачу `new → in_progress`.
- Может перевести задачу `in_progress → review`.
- Может вернуть задачу `rework → in_progress`.
- Не может менять описание задачи, объект, автора или исполнителя.

### Статусы

| Из | В | Кто |
| --- | --- | --- |
| — | `new` | Постановщик при создании |
| `new` | `in_progress` | Назначенный исполнитель |
| `in_progress` | `review` | Назначенный исполнитель |
| `review` | `accepted` | Постановщик |
| `review` | `rework` | Постановщик, комментарий обязателен |
| `rework` | `in_progress` | Назначенный исполнитель |

Другие переходы блокируются серверной функцией и триггером PostgreSQL. Проверка интерфейса не считается защитой.

## Модель безопасности

- RLS включён на `profiles`, `projects`, `tasks` и `task_status_history`.
- Исполнитель читает только задачи, у которых `assignee_id = auth.uid()`.
- Исполнитель видит объект только при наличии активной назначенной ему задачи на этом объекте.
- Роль и автор проверяются при создании задачи на стороне PostgreSQL.
- Допустимые переходы и обязательность комментария проверяются триггером и RPC `transition_task`.
- Функции с `SECURITY DEFINER` используют пустой `search_path` и полностью квалифицированные имена объектов.
- История записывается триггером. Для `anon` и `authenticated` запрещены INSERT/UPDATE/DELETE/TRUNCATE истории.
- Профили нельзя создавать или изменять через клиентский API; роль назначает администратор. Клиент читает только `id`, `full_name` и `role`, без доступа к email других пользователей.
- Удаление в интерфейсе реализовано как архивирование: `archived_at` устанавливается один раз, запись скрывается из рабочих списков, история остаётся в БД.
- Физическое удаление объектов и задач через роли `anon` и `authenticated` отозвано.
- Фронтенд использует только URL и publishable/anon key. Секретный ключ не нужен.
